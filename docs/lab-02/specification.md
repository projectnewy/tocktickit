# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a Requester-facing ticketing MVP on top of the Lab 1 TokTickIT foundation: a Requester (selected
via a temporary Development Requester selector, not real login) can create an IT support ticket with
attachments, find it in My Tickets, open its read-only Detail view, and manage its attachments — with the
backend enforcing that a Requester can never see another Requester's tickets.

## 2. Stakeholder Request Interpretation

The IT department wants requesters to self-serve: describe a problem, classify it, attach evidence, and
submit it to get an official Ticket Number. Since real login isn't ready until Lab 3, this sprint
substitutes a Development Requester Selection screen that a tester uses to choose who they're acting as.
Everything the requester can then do (create, list, search/filter/sort/page, view detail, manage
attachments) must be scoped to that selected identity only.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism, explicitly not authentication)
- Create Ticket (validation, backend-generated Ticket Number, attachments)
- My Tickets (search, filter, sort, pagination, ownership-scoped)
- Requester Ticket Detail (read-only ticket fields + attachment lifecycle)
- Attachment upload, download, and soft removal (with reason)
- Zen Green theme and reusable UI components/conventions for future labs
- REST API + PostgreSQL schema increment backing all of the above

### Excluded (per labsheet §4.2)
- Authentication and security (login, passwords, sessions, tokens, real role-based authorization)
- IT Staff workflow (queue, claiming/reassigning tickets, changing IT Priority)
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken)
- Ticket lifecycle beyond initial `New` status (resolving, closing, reopening, cancelling)
- Administration functions (managing users, roles, reference data)

## 4. Functional Requirements

- FR-01 A Requester can select a Development Requester identity from a list of active requesters before using any ticket screen.
- FR-02 A Requester can change their selected identity at any time via a visible "Switch requester" action.
- FR-03 A Requester can create a ticket by providing Category, Related System, Summary, Description, and Requested Priority.
- FR-04 On successful creation, the system displays the backend-generated, unique Ticket Number.
- FR-05 A Requester can attach 0–5 files (JPG/JPEG/PNG/WEBP/PDF, ≤5MB each) to a ticket at creation or afterward.
- FR-06 A Requester can view a paginated list of only their own tickets in My Tickets.
- FR-07 A Requester can search their tickets by Ticket Number or Summary.
- FR-08 A Requester can filter their tickets by Category, Related System, Requested Priority, and Status.
- FR-09 A Requester can sort their tickets by creation date, Ticket Number, Summary, or Requested Priority.
- FR-10 A Requester can open a Ticket Detail screen showing all ticket fields as read-only.
- FR-11 A Requester can view, upload, and soft-remove attachments from the Ticket Detail screen.
- FR-12 A Requester cannot view, list, download, or modify another Requester's ticket or attachment under any circumstance.
- FR-13 The system reflects loading, empty, no-results, and failure states on every data-driven screen.

## 5. Business Rules

- BR-01 The official Ticket Number is generated by the backend, formatted `TKT-<year>-<6 digits>`, and must be unique.
- BR-02 A new Ticket begins with Current Status `New`.
- BR-03 Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- BR-04 A ticket's `requesterId` is fixed at creation time from the currently selected Development Requester and never changes.
- BR-05 Only active Development Requesters appear in the selector; an inactive Requester cannot be selected and, if its id is ever presented as context, is rejected as if unauthenticated.
- BR-06 A Requester may access (read, list, modify) only Tickets and Attachments whose `requesterId` matches their own selected identity; access to any other Requester's data returns "not found," not an explicit "forbidden."
- BR-07 Ticket Summary is required, trimmed, 5–150 characters.
- BR-08 Ticket Description is required, trimmed, 10–4000 characters.
- BR-09 Category, Related System, and Requested Priority are required and must reference an active reference row.
- BR-10 The ticket-list query defaults to sorting by creation date, newest first, and paginates in fixed page sizes of 10, 20, or 50.
- BR-11 Submitting the Create Ticket form twice in quick succession must not create two tickets; the submit control is disabled while a request is in flight.
- BR-12 If ticket creation fails, the form's entered values are preserved so the Requester does not need to retype them.
- BR-13 An Attachment accepts only JPG, JPEG, PNG, WEBP, or PDF files, verified by both declared type and file content, and rejects anything else with a clear message.
- BR-14 An Attachment must not exceed 5 MB; oversized uploads are rejected before being fully accepted.
- BR-15 A Ticket may have at most 5 *active* (non-removed) Attachments at any time; removing one frees a slot for a new upload.
- BR-16 Removing an Attachment is a soft removal: the record and its metadata remain visible on the ticket, but the file becomes non-downloadable and non-previewable.
- BR-17 Removing an Attachment requires the Requester to confirm the action and select or enter a removal reason.
- BR-18 If a Ticket is created but one or more attachment uploads fail, the Ticket itself remains valid and saved; the Requester is shown which files failed and may retry adding them from the Ticket Detail screen.
- BR-19 An empty ticket list (no tickets at all) and a no-results list (filters matching nothing) are presented with distinct, clear messaging.
- BR-20 If the Development Requester reference list fails to load, or no active Requesters exist, the Selection screen shows a safe failure/empty state rather than a blank or broken screen.
- BR-21 Ticket Detail access by numeric id that does not exist, or that exists but is not owned by the selected Requester, both return the same "not found" outcome so existence cannot be inferred.
- BR-22 The Development Requester selection mechanism (header-based context) is designed to be replaced by real authentication in Lab 3 without changing any business rule, ownership check, or data model above.

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for the full specification. Summary: a persistent green (`#006B3C`) app
shell shows the app name, primary navigation (My Tickets / Create Ticket), and the current Requester with
a "Switch requester" action. The Development Requester Selection screen is a centered card with a
dropdown, loading/empty/failure states, and a Continue action. Create Ticket groups system-generated
fields, classification fields, Summary/Description, and Attachments, with inline validation below each
field. My Tickets shows a desktop table / mobile card list with search, filters, sort, and pagination.
Ticket Detail shows read-only ticket fields plus an Attachments section (list, upload, soft-remove).
Editable fields are white with a neutral border; read-only fields use a soft gray-green background;
errors are dark red text below the field; badges color-code Priority and Status without relying on color
alone (icon/text always included).

## 7. Data Changes

New Prisma models: `RequesterUser`, `RelatedSystem`, `Ticket`, `Attachment`, `TicketCounter`. `Category`
gains `isActive`. Two enums: `Priority` (LOW/MEDIUM/HIGH/URGENT) and `TicketStatus` (NEW/ASSIGNED/
IN_PROGRESS/RESOLVED/CLOSED/CANCELLED — Lab 2 only ever produces `NEW`; the rest exist so Lab 3 needs no
enum migration). Full field list, relations, and indexes are defined directly in
`server/prisma/schema.prisma` (source of truth); this document records the design decisions:

- **Soft removal, two representations.** Lookup tables (`Category`, `RelatedSystem`, `RequesterUser`)
  use a reversible `isActive Boolean`. `Attachment` uses `removedAt DateTime?` plus `removedReason` and
  `removedById` — a boolean cannot carry an audit trail (who removed it, why, when), which the labsheet
  requires. "Active" is computed everywhere as `removedAt == null`.
- **Index justification.** `Ticket` has `@@index([requesterId, createdAt(sort: Desc)])` because every My
  Tickets request is an equality filter on `requesterId` combined with a sort on `createdAt` and a
  limit/offset — this composite index lets Postgres serve the query without a separate sort step, and its
  cost does not grow with the number of tickets belonging to other requesters. A second index,
  `[requesterId, status, createdAt]`, extends the same shape for the status filter.
- **Search tradeoff.** Free-text search (`q`) is an unindexed case-insensitive `contains` on
  `ticketNumber` and `summary` only (not `description`), bounded by the `requesterId` equality predicate
  so it never scans the whole table. A trigram/GIN index would make it fast at scale but requires a
  Postgres extension not guaranteed to exist in the grading environment; deferred as documented future
  work rather than adopted now.
- **Ticket Number generation.** Backed by a `TicketCounter(year, lastNumber)` row, incremented inside the
  same transaction as the ticket insert via `INSERT ... ON CONFLICT(year) DO UPDATE SET lastNumber =
  lastNumber + 1 RETURNING lastNumber`. Postgres's row-level lock on the conflicting row makes concurrent
  ticket creation safe: a second transaction requesting the same year blocks until the first commits, so
  two tickets can never receive the same number. `Ticket.ticketNumber` is additionally `@unique` as a
  database-enforced backstop.
- **Lab 3 evolution.** All future needs are additive: `passwordHash String?` and `lastLoginAt DateTime?`
  on `RequesterUser`; a `Role` enum once IT Staff exists; a nullable `ownerId` FK once an IT Staff table
  exists (not added now — a nullable FK to a table that doesn't exist yet isn't expressible). No Lab 2
  column is renamed or removed by any of this.

## 8. API Contract

Full contract in `docs/lab-02/api-spec.md`. Summary: 11 requester-facing endpoints plus `/api/health`,
covering reference data (categories, related systems, requesters), ticket create/list/detail, and
attachment upload/list/metadata/download/soft-removal. The selected Requester is transmitted via an
`X-Requester-Id` header on every ticket/attachment request — chosen over a query parameter (would leak
into logs/URLs and be easy to omit on one call) or a cookie (implies session semantics Lab 2 explicitly
excludes). A missing, unknown, or inactive requester context returns `401`; cross-requester access to an
existing ticket/attachment returns `404` (identical to a genuinely nonexistent id), so the response itself
never confirms that another requester's resource exists.

## 9. Acceptance Criteria

- AC-01 Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is requested by id, then no ticket data is returned and the response is indistinguishable from a nonexistent ticket.
- AC-04 Given a required field is left empty, when the Requester submits Create Ticket, then a field-level validation message appears and no request is sent to the API.
- AC-05 Given the backend is unreachable, when the Requester submits Create Ticket, then a safe error state is shown and the entered field values are preserved.
- AC-06 Given a Ticket already has 5 active attachments, when the Requester attempts to add a 6th, then the upload is rejected with a clear message.
- AC-07 Given an attachment is removed, when the Requester views the ticket, then its metadata is still visible but its download/preview is blocked.
- AC-08 Given 14 tickets exist for the selected Requester, when My Tickets loads with the default page size, then pagination controls and total counts are shown and correct.
- AC-09 Given a search term matching no tickets, when the Requester searches, then a distinct "no results" state is shown (not the same as the empty-list state).
- AC-10 Given a Requester selects a file type outside JPG/JPEG/PNG/WEBP/PDF, when they attempt to upload it, then the file is rejected client-side and, if bypassed, rejected server-side with `415`.
- AC-11 Given a file over 5 MB, when the Requester attempts to upload it, then the upload is rejected with a clear size-limit message.
- AC-12 Given the Requester switches from Requester A to Requester B via "Switch requester," when My Tickets reloads, then Requester A's tickets are no longer visible and Requester B's tickets (if any) load instead.
- AC-13 Given the Development Requester reference list fails to load, when the Selection screen renders, then a safe failure state is shown instead of a blank screen.
- AC-14 Given no active Development Requesters exist, when the Selection screen renders, then an empty state is shown instead of an unusable dropdown.
- AC-15 Given a Ticket is created and one of two selected attachments fails to upload, when creation completes, then the Ticket is saved, the Requester is told which file failed, and they can retry it from Ticket Detail.
- AC-16 Given the app is viewed at a mobile viewport (<768px), when any of the four screens render, then no horizontal page scrolling occurs and all controls remain reachable and touch-sized.
- AC-17 Given a Requester attempts to remove an attachment, when they confirm, then a removal reason is required before the removal completes.
- AC-18 Given an inactive Development Requester's id somehow becomes the selected context, when any ticket-scoped endpoint is called, then the request is rejected with `401` as if no requester were selected.

Every criterion above maps to at least one planned test in `docs/lab-02/tests.md`.

## 11. Assumptions and Decisions

- **Cross-requester access → `404`, not `403`.** A `403` response would itself disclose that the
  resource exists but belongs to someone else. `404` is uniform with a genuinely nonexistent id. Tests
  assert both the status code and that no ticket/attachment data appears in the response body.
- **Requester context transport → `X-Requester-Id` header**, not a query parameter, body field, or
  cookie — see §8. Missing/invalid context → `401`, chosen so the client's "redirect to selector" logic
  is written once and survives unchanged when Lab 3 replaces the header with a real bearer token.
- **Removal reason UI → a fixed set of presets** ("Uploaded by mistake," "Wrong file," "Contains
  sensitive information," "No longer relevant") plus "Other" requiring free text ≤200 characters. Chosen
  over an unconstrained free-text field to keep removal data analyzable while still satisfying "confirm
  and provide a reason."
- **Files cannot be attached before a Ticket exists.** Attachment storage is keyed by `ticketId`, and
  the compensation policy on partial upload failure (§ BR-18) depends on the ticket already being
  persisted; a pre-ticket temporary-storage mechanism was considered and rejected as unnecessary
  complexity for this sprint.
- **"Ticket Owner" and "IT Priority"** appear in the labsheet's illustrative figure but belong to the
  explicitly out-of-scope IT Staff workflow. `itPriority` is added as a nullable column now (zero
  migration risk later); "Ticket Owner" has no column yet since no IT Staff table exists — the Detail
  screen shows a static "Unassigned" placeholder.
- **Ticket Detail is addressed by numeric id** (`/tickets/:id`), not by Ticket Number, for the simplest
  Prisma mapping and the clearest ownership-rejection demonstration for Part 8 of the submission.
- **An inactive Requester's existing tickets are retained**, not hidden or deleted; only the selector
  and the requester-context check treat them as unavailable going forward.
